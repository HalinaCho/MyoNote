## 1. Phase 3 재설계 — 위치 매칭 시점을 "저장 후" → "입력 시작 시"로 (`e48ac51`)

실기기 검증에서 나온 첫 피드백: 위치 매칭으로 테스트안과에 연결됐다는 토스트는 떴는데, **다음 검사를 추가할 때 "안과" 칸이 여전히 비어 있었다.**

원인은 두 개념이 서로 모르는 사이였던 것.
- `clinic`은 순수 자유입력 텍스트고, 새 기록의 기본값은 `exams[0].clinic`(직전 기록에 손으로 친 병원명)이었다. 첫 기록에 병원명을 안 쳤으니 계속 빈칸.
- 위치 매칭이 **저장이 끝난 뒤** 실행돼서, 방금 저장된 기록에 되돌려 반영할 곳이 없었다. `entered_by_hospital_id`도 안 붙어 원장 포털에서 "우리 병원 입력"으로 안 잡혔다.

매칭을 **검사 입력 모달을 여는 시점**으로 옮겨 해결. 스태프가 병원에서 폼을 여는 순간이 곧 방문이므로 시점상으로도 맞다.
- 페이지 진입 시 담당 병원을 미리 조회 → `+추가`를 누르면 안과 칸이 바로 채워짐(위치 권한과 무관)
- 모달 열 때 위치로 병원 확정(전환 포함), 병원이 **바뀐 경우에만** 토스트
- 안과 칸을 직접 고치면 자동입력이 덮어쓰지 않음(`clinicTouchedRef`)
- 저장 시 **병원 현장 입력일 때만** `entered_by_hospital_id` 태깅 + 보호자 알림. 집에서 부모가 넣은 기록은 알림 대상이 아니다 — 기존엔 이 구분이 없었다

## 2. Phase 6 — 순응도 컬럼 + 환자 상세 (`873994a`, `62b8708`)
SQL: `docs/sql/2026-08-27-clinic-patient-detail.sql`
- `hospital_patient_care`(순응도 원자료), `hospital_patient_detail`(환자 상세)
- **순응도 %는 클라이언트에서 계산**한다. "그날 활성인 케어" 판정이 `treatments` JSONB의 periods 기반이라 SQL로 옮기면 부모 앱과 로직이 이중화된다. `calcRecentCompliance`(최근 N일) 추가 + `makeTreatmentsForDate`로 케어 정의 배열만 있어도 날짜별 판정이 되게 함
- 환자 목록에 7일/30일 순응도(80↑ 초록 / 50↑ 주황 / 미만 빨강), 행 클릭 시 상세로
- `/clinic/patients/[childId]` — 검사 이력(안축장 + 직전 대비 변화량, SEQ), 우리 병원 입력 표시. **이탈한 환자는 열람 불가** — 옮겨간 병원의 진료 내용이 노출되므로 RPC에서 활성 연결로 제한
- 이어서 환자 목록에 생년월일(동명이인 구분) + 이름 검색. 최근 검색어는 localStorage, 현재 검색어는 sessionStorage(상세에 갔다 돌아와도 필터 유지). 최근 검색어는 엔터·환자 선택처럼 검색이 "완료"된 시점에만 쌓는다

## 3. Phase 5 — 부모 홈 개편 (`8193c8e`, `0de4961`)
홈을 "매일 입력하는 화면"에서 "병원이 준 결과를 보는 화면"으로.
- 병원 브랜딩 헤더 / "새 검사 결과 도착" 배너 / 병원 공지 / 다음 예약(기존 로직 유지)
- "오늘의 케어 체크"·"오늘의 생활습관"은 삭제하지 않고 캘린더 탭으로 이동
- `AiReportCard`: 마지막 리포트 이후 새 검사가 있으면 마운트 시 1회 자동 생성(자녀당 1회 가드 — 실패해도 재시도 루프 없음). `hasUnseenExam` 신설, `ExamRecord`에 `createdAt` 추가
- **후속 버그**: 탭을 옮겨 홈에 올 때마다 병원 헤더만 한 박자 늦게 떴다. 홈이 마운트될 때마다 병원을 새로 조회했기 때문. `ChildProvider`는 대시보드 레이아웃에 살아있으므로 병원 조회를 **`ChildContext`로 올려** 자녀 데이터와 함께 1회만 로드 → 탭 이동 시 재조회 자체가 사라짐. 검사입력 화면의 중복 조회도 같이 제거

## 4. Phase 7 — 브랜딩 + 병원 소식 피드 (`70ab03b`, `373b3d8`)
SQL: `docs/sql/2026-08-27-hospital-branding-feed.sql`

공지를 단발 텍스트로 만들려다, 사용자가 **SNS 피드 형태**(글마다 사진·영상 혼합, 여러 개 누적)를 요구해 설계를 바꿨다.
- 신규 테이블 `eyebody_hospital_posts` — 본문 + 이미지 배열(최대 5장, **DB check 제약으로 강제**) + 유튜브 링크. 부모는 "현재" 연결된 병원 글만 읽을 수 있게 RLS(`superseded_at is null`)
- 첫 Storage 버킷 `hospital-media` — 로고와 소식 이미지를 한 버킷에서 쓴다. 경로 첫 폴더가 병원 id라는 규칙 하나로 정책이 둘 다 커버(`is_hospital_staff((storage.foldername(name))[1]::uuid)`)
- **이미지 5장 / 유튜브 임베드로 정한 근거**: Supabase 무료 플랜에서 병목은 저장 용량(1GB)이 아니라 **월 전송량(5GB)**. 리사이즈 후 장당 ~150KB라 저장은 병원 500곳×10장도 여유지만, 부모가 홈을 열 때마다 나가는 전송량이 한도를 정한다. 동영상 파일 업로드는 한 편에 수십 MB라 무료 전송량을 하루에 태우므로, 재생 트래픽을 유튜브가 부담하는 임베드가 유일하게 현실적
- `/clinic/posts` 신규 탭(작성·수정·삭제), `/clinic/settings` 브랜딩 섹션(로고·컬러 + **부모 홈 실시간 미리보기** — 원장은 저장 후 부모 폰으로 확인하러 갈 수 없다)
- 부모 홈: 최신 소식 1개를 피드처럼 그대로(영상 임베드 포함), 전체는 바텀시트. 새 라우트·새 탭 없이 시트로 처리해 부모 앱 탭 구조를 안 건드림
- `downscaleImage`에 출력 MIME 인자 추가 — 기존 구현이 JPEG 고정이라 **투명 배경 로고가 흰 사각형으로 뭉개졌다.** 로고만 PNG로
- `utils/color.ts` — 배경 밝기로 글자색 자동 선택. 색을 프리셋으로 가두는 대신 어떤 색을 골라도 병원 이름이 읽히게. `utils/youtube.ts` — 공유링크·주소창·쇼츠 세 형태 파싱, nocookie 도메인 임베드
- `eyebody_hospitals.notice` 컬럼 제거. **`get_my_hospital`이 그 컬럼을 리턴하고 있어서 컬럼만 지우면 깨진다** — 함수를 먼저 갈아끼우도록 SQL 순서를 잡음(리턴 컬럼 구성이 바뀌어 `create or replace` 불가, `drop function` 필요)

## 5. 실기기 피드백 반영 2차 (`ff4d4e6`, `0b2d611`, `2c36bd6`, `ecbb370`)

### 브랜드 컬러 스포이드 — 한 번에 못 고친 건
"스포이드를 누르면 색상 선택창이 로고를 가린다"는 지적에 **스포이드 버튼만 옆에 추가**했는데, 색상 대화상자를 여는 경로(색상 네모칸)를 그대로 둬서 해결이 안 됐다. 다음 시도에서 네이티브 색상 입력을 아예 빼고 색상표+HEX로 갈아치웠더니 이번엔 "색상표는 의미없다, 원래대로 피커를 달라"는 답. 최종은 **피커는 유지 + 별도 스포이드 버튼이 열려 있던 팝업을 `blur()`로 닫고 실행**.
- 남은 한계: 색상칸 팝업 **안에 딸린 브라우저 자체 스포이드**는 팝업을 띄운 채 동작하고, JS로 그 팝업을 닫을 방법이 없다. 안내 문구로 별도 버튼을 쓰도록 유도하는 선에서 합의

### 병원 헤더 — 카드처럼 보이는 문제
카드들과 같은 여백·둥근 모서리 안에 있어 "여러 카드 중 첫 번째"로 읽혔다. 풀블리드 띠(`ff4d4e6`) → 여전히 콘텐츠 같다는 피드백 → **히어로**(`0b2d611`): 띠를 높이고 아래를 비운 뒤 카드 묶음을 음수 마진으로 끌어올려 겹치게. 겹침이 생기면 병원 영역이 배경으로 물러난다. (디자인은 나중에 다시 손보기로)

### 소식 카드를 진짜 피드처럼
홈 카드에 텍스트만 보이고 영상은 눌러 들어가야 보였다 → 유튜브를 홈에서 바로 재생, 사진은 첫 1장만 크게(나머지는 "사진 N장" 배지), 본문 4줄 + "더보기". **카드 전체를 버튼으로 감싸던 걸 풀었다** — 안에 iframe과 더보기가 들어가 클릭이 서로 잡아먹는다. 시트 열기는 헤더의 "전체 N개" 버튼으로 분리

## 6. 캘린더 탭 → 케어 탭 재구성 (`dbacec3`, `4b939d1`)

Phase 5에서 홈의 케어 항목을 캘린더 탭으로 옮긴 결과, 한 화면에 **섹션 7개**가 쌓였다(배너·오늘케어·오늘생활습관·월간캘린더·최근7일케어·최근7일생활습관·월평균비교). "매일 하는 입력"과 "가끔 보는 조회"가 섞인 게 원인.

- 하단 탭 **캘린더 → 케어**(아이콘도 달력 → 체크). 이 탭의 주된 행동은 기록이지 달력 보기가 아니다. 라우트는 유지
- 첫 화면은 카드 3개: **케어 현황**(연속 달성·이번 달·이번 주 스트립) → 오늘의 근시케어 → 오늘의 생활습관. 스크롤 없이 끝난다
- 캘린더·통계는 `/calendar/history` 한 화면으로 통합하고 상단 [캘린더][통계] 토글. **한 화면에 그냥 쌓으면 첫 화면에서 없앤 문제가 그쪽으로 옮겨갈 뿐**이라 토글로 나눠 각각 짧게 유지. 입구는 "케어 현황" 카드 우상단 "기록 보기" 하나
- **삭제 2건(정보 손실 없음)**: '최근 7일 근시케어' 섹션은 월간 캘린더가 같은 정보를 더 넓게 보여줘 중복 — 값어치 있던 스트릭·이번달%·주간 스트립만 흡수. '케어 미기록' 배너는 오늘의 케어 체크가 맨 위로 와서 역할이 겹침
- 날짜별 기록 시트를 `DayDetailSheet`로 분리(오늘 화면·캘린더 공용). **`key={date}`로 마운트**해 날짜가 바뀌면 `useState` 초기값이 다시 잡히게 — effect 동기화가 필요 없고 Next 16의 `react-hooks/set-state-in-effect` 린트도 통과

## 검증
- 전 단계 `tsc --noEmit` + 신규/변경 파일 `eslint` 클린, `npm run build` 성공(라우트 22개)

- 사용자 실기기 확인 완료: 안과 칸 자동입력 / 로고 즉시 반영 / 밝은 색에서 글자색 자동 전환 / 케어 탭 두 경로(주간 스트립·캘린더)에서 동일한 수정 시트
